## profile 详情仍显示乱码/零值 → DB phases_json 是旧垃圾

用户截图反馈 profile 详情页阶段名乱码、Target 0.0 bar in 0s、曲线空白；同时询问首页「当前曲线」图表含义。用户已连上手机，我通过 adb pull 了 `/data/data/com.gagmate.app/databases/gagmate.db`。

### 数据库检查结果
- `profiles.phases_json` 对多数 `SYNCED` profile 存的是损坏数据：`name` 字段含原始 protobuf 字节，`target=0.0`、`time=0.1`、`variation="FLAT"`。与截图完全吻合。
- `turbo shot` 等少数 profile 的 `phases_json = "[]"`。
- 首页「当前曲线」走联网实时 `fetchProfilePhases`，不依赖本地 `phases_json`，所以能画出曲线；profile 详情回退到本地库时展示垃圾。

### 根因
1. 旧版 WS 相位解码器把 protobuf 字节写进 `name`，且 target/time 全零。当前 WS→Room 收集器已丢弃 all-zero，但旧数据未清理。
2. `SyncManager.syncProfiles` 的 REST 真实曲线回写被 `machineSession.isConnected()` 卡住；启动 500ms 时 WS 通常未握手，导致 REST 取数分支被跳过，垃圾永不被覆盖。

### 修复（已 `assembleDebug` 绿，未提交）
- `AppDatabase.kt`：`version=5`，新增 `MIGRATION_4_5`，将 `SYNCED` profile 的 `phases_json` 重置为 `"[]"`，清掉旧垃圾。
- `SyncManager.syncProfiles`：去掉 REST 回写前的 `machineSession.isConnected()` 判断；把「已真实」条件改为：空 / 全零 / 全部 FLAT/LINEAR 都重新取 REST 详情。

### 文档
- `GAGMATE_REFERENCE.md`：版本 5、新增 `MIGRATION_4_5` 说明、更新 `syncProfiles` 描述；顶部日期→2026-07-29。
- `CODE_REVIEW.md`：新增 **§0i** 记录本轮；顶部日期→2026-07-29。

## 复盘 `gagmate_combined(6).log`：上一轮修复前提被推翻

用户再发 07-28→07-29 的日志（`gagmate_combined(6).log`）让我参考。关键发现：

### 1. `GET /api/profile/{id}` 本机固件返回的是 SPA HTML，不是 JSON
- 重连后 `SyncManager.syncProfiles` 遍历所有 profile 调 `GET /api/profile/{id}`（8/17/19/18/27/15/.../33），**每条都返回 `<!DOCTYPE html>...<title>Gaggiuino</title>` 的 index.html**。
- 所以 599e4b7 的「REST 回写真实 EASE_* 曲线」分支**永远拿不到数据**；`MIGRATION_4_5` 把 `phases_json` 清成 `[]` 后，没有任何东西再回填 → profile 详情持续空白。这解释了「改完还是没数据」。

### 2. WS `d_prof` 确实在推送每个 profile 的完整 phase（日志 22601+ 行有 protobuf）
- 但 `ProtoDecoder.decodePhaseInfo` 的字段映射与本机固件不一致：把真实 target 字节误读成「name」，start/end/curve 全零 → variation 恒 `FLAT`。
- 手工按真实 schema 解析 d_prof phase：`fn1`=type、`fn2`=嵌套(target/start/time)、`fn3`/fn4=float/嵌套，但**全程找不到 0–6 的 curve 枚举** → 印证「WS d_prof 不携带 curve 类型」。

### 3. 唯一真能拿到真实 EASE_* 曲线的来源 = shot 内嵌 `profile.phases`
- `GET /api/shots/24` 返回 `{"profile":{"id":33,"name":"turbo shot","phases":[{"target":{"end":3.5,"curve":"EASE_OUT","time":5000}...`
- 全日志 grep 到 `"curve":"EASE_IN"`×26、`"curve":"EASE_OUT"`×52。
- 这正是之前**仪表盘「当前曲线」联网时能画缓动曲线**的来源——detail 页没接这个回退，所以一直空白/乱码。

### 结论 / 下一步建议（待用户确认）
- 本机固件的「曲线定义」权威来源 = **shot 内嵌 profile**（REST `/api/shots/{id}`）；`/api/profile/{id}` 死、WS d_prof 无 curve。
- 需改写 `fetchProfilePhases` / `syncProfiles` 的取数：优先用「按 profile id/name 匹配的最新 shot 内嵌 phases」作为曲线+值来源，回退 d_prof（需先修解码器才能拿到真实值，但仍缺 curve）。
- 这会与 CODE_REVIEW §0e「shot 不能作为离线权威」的早前判断冲突，需用户拍板是否接受 shot 作为**展示/曲线**来源。

## 热修（下午）：MIGRATION_5_6 可空性不一致 → 触库页面闪退
- 用户报：萃取历史 tab、导出崩溃日志页点开即闪退。
- 根因：`MIGRATION_5_6` 首版把 `profile_id` 建成 `TEXT NOT NULL DEFAULT ''`，但 `ShotEntity.profileId` 是 `String?` → Room 迁移后 schema 校验抛 `Migration didn't properly handle: shot_records`；迁移事务回滚（DB 停留 v5、数据无损），每次触库重复失败 → 触库页面全部闪退（仪表盘走 WS 无感）。
- 修复：迁移 SQL 改 `ALTER TABLE shot_records ADD COLUMN profile_id TEXT`（可空、无默认）；`embedded_phases_json` 保持 `NOT NULL DEFAULT '[]'`。BUILD SUCCESSFUL。
- **教训（长期）**：Room Migration 新增列的可空性/默认值必须逐字对齐 Entity 声明（`String?` → 可空 TEXT；非空 `String` → `NOT NULL DEFAULT`）；涉及迁移的改动上机前应实测一次升级路径。
